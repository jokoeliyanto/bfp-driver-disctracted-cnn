Why ship the lower-scoring model?

On paper the baseline wins by {{ baseline.best_val_accuracy|floatformat:4 }} vs {{ deployed.best_val_accuracy|floatformat:4 }}. We still deployed MobileNet:

  • The gap is one point on a leaky split (next card). A validation set that shares drivers with training rewards memorising them, which says little about new drivers.
  • The baseline learns all {{ baseline.params.total|millions }} weights from 26 drivers. MobileNet's frozen ImageNet features cannot memorise those drivers, so it has less room to overfit.
  • It was still improving. Validation loss fell at every one of the {{ deployed.epochs_run }} epochs, so more epochs or fine-tuning would likely close the gap.
  • It trains {{ baseline.seconds_per_epoch|floatformat:0 }}/{{ deployed.seconds_per_epoch }} ≈ 6× faster per epoch and is built from mobile-friendly depthwise-separable convolutions.

How far to trust 98%

The validation set was made with Keras' validation_split=0.2, which simply takes 20% of each class folder. The State Farm photos are consecutive frames of {{ metrics.dataset.n_drivers }} drivers, so the same people, in the same car and clothes, appear in both training and validation. Near-duplicate frames make validation look much easier than real use.

The honest test for this product is a split by driver (for example, GroupKFold on the subject column of driver_imgs_list.csv): train on some drivers, measure on people the model has never seen. That is what a real customer is. Until then, read 98% as an upper bound.

Audit of the 2020 notebook

Revisiting the project turned up four things a reviewer should know. None changes the published weights; all are handled in this web app.

1

The published weights expect raw pixels, not the notebook's 0–1 scaling

The notebook's generators use rescale=1./255, but the TensorFlow.js model in models/tfjs only works on raw 0–255 values. On the eight example frames, raw input gives {{ check.raw_0_255.distinct_classes }} different activities with spread {{ check.raw_0_255.spread }}; rescaled input gives the same class for all eight (spread {{ check.rescaled_0_1.spread }}), the signature of an input-range mismatch. The architecture and parameter count ({{ metrics.deployed.params|thousands }}) match the notebook exactly, so the published file is a run of the same model trained without rescaling. The app feeds raw pixels.

2

Class order: Kaggle codes, not the notebook's folder names

In the notebook the folders were renamed ("Doing Hair or Makeup", "Drinking", …), so Keras sorted the classes alphabetically into a different order. The published model and models/labels.txt follow the Kaggle order c0–c9, which is the one that gives sensible predictions on the example frames (for instance, the frame of a woman who appears to be drinking → c6 drinking, and two drivers holding a phone to the ear → c2). The app uses the c0–c9 order.

3

The "improvement model" plot repeats the baseline curves

The plotting cell after the MobileNet run calls plot_train_history(history), the baseline history, instead of history1. The curves above are re-drawn from the logged numbers of both runs.

4

Saved outputs come from more than one session

The MobileNet log shows 18 steps per epoch, which implies batches of about 1,000 images, while the code says BATCH_SIZE = 16; and the optimizer stored in model.json uses a learning rate of 0.001 rather than the notebook's 1e-5. The numbers on this page are taken from the logs as saved.
